# Naming

Именование — процесс **субъективный и сценарно-ориентированный**. Этот skill — **фреймворк**, а не свод правил: он не вшивает субъективные правила именования.

## Быстрая схема

```
┌─────────────────────────────────────────────────────────┐
│  1. ИССЛЕДОВАНИЕ цели                                   │
│     Что именуется? Какую роль играет? Какое понятие?    │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  2. naming.<user-task>.yml  (файл .rule)                │
│     - goal-*        (задача именования)                  │
│     - keyresult-*   (верифицируемые результаты)          │
│     - task-*        (ограничения задачи)                │
│     - session:      (журнал аудита goal-правила)         │
│         prefer     (5 ответов init-004)                  │
│         init_verdicts (решения по гейтам для кандидатов) │
│         scores      (D1-D7 с обоснованием)              │
│         final       (выбор + запасной)                  │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  3. АУДИТ через template/naming.okr-creator.yml         │
│     x rule check -r <naming-dir> naming.<user-task>.yml │
└─────────────────────────────────────────────────────────┘
```

## Рабочий процесс — шаг за шагом

### Шаг 1 · Исследование цели

Прежде чем что-либо писать, ответьте на эти вопросы. НЕ пропускайте — без ответов scorer не сможет привязать D4 (TRIAL/REAL) или D5 (RUN/TEST).

- **Что именуется?** — модуль / подкоманда / поле / переменная — для разных форм имён действуют разные правила
- **Какую роль это играет?** — фиксирует понятие (например, «модуль trial-run» → самостоятельный раннер, стадия 1 двухстадийного теста)
- **Какой смысл ОБЯЗАН нести?** — доминирующее значение слова должно совпадать (например, trial-run требует TRIAL+RUN, а не REAL+TEST)
- **Каких смыслов ОБЯЗАН избегать?** — загрязнение unittest (`*test`/`*case`), фейк (`*mock`/`*fake`/`*stub`/`*dry`), реальный деплой (`field*`/`*live*`)
- **Какой архетип подходит?** — корабль / самолёт / ракета / фабрика / абстракция — определяет D6/D7

Результат: однострочное описание цели, например
> «Подобрать имя самостоятельного модуля x-cmd для trial-run (стадия 1 двухстадийного теста) с оценкой 8.0+ по D1-D7, очевидное с первого взгляда и проходящее все fast-fail по красной линии / словарю / длине.»

### Шаг 2 · Создание журнала сессии

Скопируйте шаблон и обрежьте / заполните.

```bash
cp naming.template.yml naming.<user-task>.yml
```

Затем заполните 4 раздела (сверху вниз):

#### 2a. Goal-правило (задача именования)

Замените `goal-TBD_task_id` реальным ID. Суффикс ID должен отражать задачу (например, `goal-trial-run-naming`, `goal-mvp-prerelease-subcmd`).

```yaml
goal-trial-run-naming:
  name: <однострочное описание цели из шага 1>
  apply: "naming.<user-task>.yml (self)"
  level: error
  desc:
  - <понятие + роль + запретные смыслы, из шага 1>
```

#### 2b. Key results (верифицируемые результаты)

Замените каждый `keyresult-kr*_TBD_short_label`. Каждый KR — это правило, которое должно проходить проверку. Добавьте столько, сколько требует задача.

```yaml
keyresult-kr1-top-pick-committed:
  name: <верифицируемый результат 1>
  level: error
  desc:
  - <что считается прохождением — конкретный критерий, а не «выглядит хорошо»>
```

#### 2c. Правила задачи (ограничения на кандидатов)

Замените каждый `TBD_task_id-*` реальным ID ограничения, совпадающим по суффиксу с task-id цели. Нерелевантные удалите, добавьте новые по необходимости.

Типовые шаблоны:
- `must-be-X-not-Y` — выравнивание понятия (например, `must-be-TRIAL-not-REAL`)
- `length-N-to-M-letters` — жёсткий диапазон D1
- `must-imply-<archetype>` — привязка к D7
- `<domain>-specific-acceptable` / `not-acceptable` — узкоспециализированное допущение
- `must-be-self-explanatory` — D3

```yaml
trial-run-001:
  name: <ограничение, например «must-be-TRIAL-not-REAL»>
  apply: "candidate words for <task-id>"
  level: error | warn
  desc:
  - <что кандидат должен удовлетворять>
  - <какое измерение D1-D7 это ограничивает>
  tldr:
  - wrong: <отрицательный пример>
  - right: <положительный пример>
```

#### 2d. Журнал сессии (аудит-trail для goal-правила)

Заполните все 4 подраздела:

**prefer** — ОБЯЗАН ответить на все 5 вопросов, даже если ответ «no / weak»:
```yaml
prefer:
  vivid: yes | no | weak
  domain_acceptable: [<список допустимых узких доменов, например [naval]>]   # [] = нет допустимых узких доменов
  length_priority: shorter | self_explanatory
  origin: english | chinese | coined
  trade_off: single_prior_ok | hit_every_dim
```

**init_verdicts** — запись на каждый рассмотренный кандидат, включая отклонённых:
```yaml
init_verdicts:
  - { name: <кандидат>, gate: init-005 | init-006 | init-007 | pass, reason: "<почему>" }
  # init-005 = срабатывание шаблона красной линии (авто-отклонение)
  # init-006 = первое значение словаря противоречит цели
  # init-007 = длина вне диапазона (< 2 или > 8)
  # pass     = прошёл все init-гейты, допущен к оценке
```

**scores** — запись на каждого кандидата, прошедшего init. Все оценки >= 6.0. Каждая оценка ОБЯЗАНА иметь обоснование:
```yaml
scores:
  - name: <кандидат>
    score: <0_to_10>
    anchors:
      - "D1: <обоснование по числу букв>"
      - "D2: <обоснование по первому значению словаря>"
      - "D3: <обоснование по составному значению>"
      - "D4: <обоснование trial vs real>"
      - "D5: <обоснование run vs test>"
      - "D6: <обоснование образности>"
      - "D7: <обоснование крупной техники>"
    misses:
      - "<что отсутствует — перечисляйте только реальные пропуски, не всегда все 7>"
```

**final** — объявите выбор и запасной вариант:
```yaml
final:
  pick: <победивший_кандидат>
  backup: <второе_место_или_null>
```

### Шаг 3 · Аудит мета-правилом

```bash
x rule check -r <naming-dir> naming.<user-task>.yml
```

OKR-creator (по пути `template/naming.okr-creator.yml`) выполняет 11 проверок (смесь error и warn):

| Проверка | Уровень | Что проверяет |
|---|---|---|
| `okr-creator-001` has-goal-rule | error | в файле есть ≥1 правило `goal-*` |
| `okr-creator-002` has-keyresult-rules | error | в файле есть ≥1 правило `keyresult-*` |
| `okr-creator-003` has-task-specific-rules | error | в файле есть ≥1 правило задачи (не goal/keyresult) |
| `okr-creator-010` has-session-record | error | goal-правило имеет поле `session:` |
| `okr-creator-011` prefer-answers-all-five | error | все 5 вопросов init-004 отвечены |
| `okr-creator-012` init-verdicts-recorded | error | init_verdicts не пуст |
| `okr-creator-013` scores-have-anchors | error | у каждой оценки непустой список anchors |
| `okr-creator-014` scores-no-below-6 | error | все оценки >= 6.0 |
| `okr-creator-015` final-section-present | error | объявлен `final.pick` |
| `okr-creator-020` pick-backup-gap-le-1 | warn | score(pick) - score(backup) <= 1.0 |
| `okr-creator-021` top-pick-at-least-7 | warn | оценка pick >= 7.0 |

**Если какая-либо error-проверка не проходит**: исправьте файл и запустите снова. Типовые исправления:
- Отсутствует поле prefer → добавьте в `session.prefer`
- Голый score → добавьте `anchors: [...]`
- Score < 6 → перенесите в `init_verdicts` (отклонён) или переформулируйте оценку
- Отсутствует final → добавьте `final: { pick, backup }`

**Если не проходят warn-проверки**: решите, исправлять ли, либо задокументируйте компромисс.

### Шаг 4 · Пользователь выбирает финальное имя

Skill предлагает; пользователь решает. Финальное имя объявляется в `session.final.pick` и фиксируется.

## Разделение субъективного и объективного

| Объективное (в файлах / коде) | Субъективное (спрашивается на init, не оценивается) |
|---|---|
| Первое значение в словаре | «Хочу образное или абстрактное» |
| Число букв | «Хочу допустимый домен X» |
| Семантический класс Trial / Real / Run / Test | «Хочу ли допустимую морскую метафору» |
| Составное буквальное значение | «Хочу китайское или английское происхождение» |
| Загрязнение смыслов (unittest testcase, dryrun) | «Хочу короткое, а не самообъясняющее» |

## Правила

- **ОБЯЗАН** сначала исследовать цель — что именуется, какую роль играет, какое понятие фиксирует.
- **ОБЯЗАН** отталкиваться от `naming.template.yml` (плейсхолдеры TBD_*) и обрезать / заполнять под задачу.
- **ОБЯЗАН** сгенерировать `naming.<user-task>.yml` (формат `.rule`) с goal / key results / task rules / session record.
- **ОБЯЗАН** запустить `x rule check` с `template/naming.okr-creator.yml` для аудита журнала сессии.
- **ОБЯЗАН** привязывать оценки к объективным фактам — никогда не завышать / не занижать их в зависимости от реакции пользователя.
- **ОБЯЗАН** позволить пользователю выбрать финальное имя — skill предлагает, пользователь решает.
- **ЗАПРЕЩАЕТСЯ** добавлять субъективные правила в `template/naming-concept.yml` — они идут в `session.prefer` конкретной задачи.
