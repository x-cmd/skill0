# Naming

การตั้งชื่อเป็นเรื่อง **อิงความเห็นส่วนตัวและบริบทการใช้งาน** สกิลนี้เป็น **กรอบคิด** ไม่ใช่คู่มือกฎ — ไม่มีการฝังกฎการตั้งชื่อที่เป็นเรื่องดีวินาจินเข้าไป

## แผนที่ย่อ

```
┌─────────────────────────────────────────────────────────┐
│  1. สืบสวนเป้าหมาย                                      │
│     กำลังตั้งชื่ออะไร? บทบาทเป็นอะไร? แนวคิดคืออะไร?  │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  2. naming.<user-task>.yml  (ไฟล์ .rule)               │
│     - goal-*        (งานการตั้งชื่อ)                    │
│     - keyresult-*   (ผลลัพธ์ที่ตรวจสอบได้)            │
│     - task-*        (ข้อจำกัดเฉพาะงาน)                │
│     - session:      (ร่องรอยการตรวจสอบบน goal rule)   │
│         prefer     (คำตอบ 5 ข้อของ init-004)          │
│         init_verdicts  (ผลตัดสินต่อตัวเลือกแต่ละตัว)   │
│         scores     (ยึดหลักฐาน D1-D7 ต่อตัวเลือก)     │
│         final      (เลือกตัว + ตัวสำรอง)              │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  3. ตรวจสอบด้วย template/naming.okr-creator.yml         │
│     x rule check -r <naming-dir> naming.<user-task>.yml │
└─────────────────────────────────────────────────────────┘
```

## ขั้นตอนทีละขั้น

### ขั้นที่ 1 · สืบสวนเป้าหมาย

ก่อนเขียนอะไรทั้งสิ้น ให้ตอบคำถามเหล่านี้ ห้ามข้าม — ถ้าไม่มีคำตอบ ผู้ให้คะแนนจะยึดหลัก D4 (TRIAL/REAL) หรือ D5 (RUN/TEST) ไม่ได้

- **กำลังตั้งชื่ออะไร?** — โมดูล / คำสั่งย่อย / ฟิลด์ / ตัวแปร — กฎรูปแบบชื่อต่างกันไป
- **มันทำหน้าที่อะไร?** — เป็นจุดยึดของแนวคิด (เช่น "โมดูลทดลองรัน" → ตัวรันแยกต่างหาก เป็นขั้นที่ 1 ของการทดสอบสองขั้นตอน)
- **ต้องแบกความหมายเดิม (prior) ใด?** — ความหมายแบบคำเดี่ยวที่โดดเด่นต้องตรงกัน (เช่น trial-run ต้องการ TRIAL+RUN ไม่ใช่ REAL+TEST)
- **ต้องหลีกเลี่ยงความหมายเดิมใด?** — การปนเปื้อนจาก unittest (`*test`/`*case`) ปลอม (`*mock`/`*fake`/`*stub`/`*dry`) การใช้งานจริง (`field*`/`*live*`)
- **เข้ากลุ่มต้นแบบ (archetype) ไหน?** — ship / plane / rocket / factory / abstract — ขับเคลื่อน D6/D7

ผลลัพธ์: ข้อความเป้าหมายหนึ่งบรรทัด เช่น
> "เลือกชื่อโมดูล x-cmd แบบใช้ลำพังสำหรับ trial-run (ขั้นที่ 1 ของการทดสอบสองขั้นตอน) ที่ได้คะแนน 8.0+ ใน D1-D7 อธิบายได้ด้วยตัวเองเมื่อมองเห็นครั้งแรก และผ่านการตรวจสอบล้มเหลวเร็วทุกข้อทั้งเส้นแดง / พจนานุกรม / ความยาว"

### ขั้นที่ 2 · สร้างบันทึกเซสชัน

คัดลอกเทมเพลตแล้วตัดส่วน / เติมข้อมูล

```bash
cp naming.template.yml naming.<user-task>.yml
```

จากนั้นเติมข้อมูล 4 ส่วน (จากบนลงล่าง):

#### 2a. Goal rule (งานการตั้งชื่อ)

แทน `goal-TBD_task_id` ด้วย ID จริง ส่วนท้ายของ ID ควรสะท้อนงานนั้น (เช่น `goal-trial-run-naming`, `goal-mvp-prerelease-subcmd`)

```yaml
goal-trial-run-naming:
  name: <ข้อความเป้าหมายหนึ่งบรรทัดจากขั้นที่ 1>
  apply: "naming.<user-task>.yml (self)"
  level: error
  desc:
  - <แนวคิด + บทบาท + prior ที่ต้องหลีกเลี่ยง จากขั้นที่ 1>
```

#### 2b. Key results (ผลลัพธ์ที่ตรวจสอบได้)

แทนแต่ละ `keyresult-kr*_TBD_short_label` แต่ละ KR คือกฎที่ต้องผ่านได้ เพิ่มได้เท่าที่งานต้องการ

```yaml
keyresult-kr1-top-pick-committed:
  name: <ผลลัพธ์ที่ตรวจสอบได้ 1>
  level: error
  desc:
  - <อะไรที่ถือว่าผ่าน เกณฑ์ที่เป็นรูปธรรม ไม่ใช่ "ดูดีแล้ว">
```

#### 2c. กฎเฉพาะงาน (ข้อจำกัดของตัวเลือก)

แทนแต่ละ `TBD_task_id-*` ด้วย ID ข้อจำกัดจริงที่ตรงกับ task-id ของ goal ตัดทิ้งข้อที่ไม่เกี่ยว และเพิ่มของใหม่ได้ตามความจำเป็น

รูปแบบที่พบบ่อย:
- `must-be-X-not-Y` — การจัดแนวแนวคิด (เช่น `must-be-TRIAL-not-REAL`)
- `length-N-to-M-letters` — ช่วงความยาวแข็งของ D1
- `must-imply-<archetype>` — ข้อผูกมัดของ D7
- `<โดเมน>-specific-acceptable` / `not-acceptable` — การอนุญาตแบบแคบเฉพาะโดเมน
- `must-be-self-explanatory` — D3

```yaml
trial-run-001:
  name: <ข้อจำกัด เช่น "must-be-TRIAL-not-REAL">
  apply: "candidate words for <task-id>"
  level: error | warn
  desc:
  - <สิ่งที่ตัวเลือกต้องทำตาม>
  - <มิติ D1-D7 ข้อใดที่ข้อจำกัดนี้ควบคุม>
  tldr:
  - wrong: <ตัวอย่างที่ผิด>
  - right: <ตัวอย่างที่ดี>
```

#### 2d. บันทึกเซสชัน (ร่องรอยการตรวจสอบบน goal rule)

เติมทั้ง 4 ส่วนย่อย:

**prefer** — ต้องตอบทั้ง 5 คำถาม แม้คำตอบจะเป็น "no / weak":
```yaml
prefer:
  vivid: yes | no | weak
  domain_acceptable: [<รายการโดเมนแคบที่ยอมรับได้ เช่น [naval]>]   # [] = ไม่ยอมรับโดเมนแคบเลย
  length_priority: shorter | self_explanatory
  origin: english | chinese | coined
  trade_off: single_prior_ok | hit_every_dim
```

**init_verdicts** — หนึ่งรายการต่อหนึ่งตัวเลือกที่พิจารณา รวมถึงตัวที่ตัดทิ้ง:
```yaml
init_verdicts:
  - { name: <ตัวเลือก>, gate: init-005 | init-006 | init-007 | pass, reason: "<เหตุผล>" }
  # init-005 = ตรงกับรูปแบบเส้นแดง (ตัดออกอัตโนมัติ)
  # init-006 = ความหมายแรกตามพจนานุกรมขัดกับเป้าหมาย
  # init-007 = ความยาวเกินช่วง (< 2 หรือ > 8)
  # pass     = ผ่านทุกประตู init มีสิทธิ์เข้าสู่การให้คะแนน
```

**scores** — หนึ่งรายการต่อหนึ่งตัวเลือกที่ผ่าน init คะแนนทุกตัวต้อง >= 6.0 คะแนนทุกรายการ **ต้อง** มีหลักฐานยึด:
```yaml
scores:
  - name: <ตัวเลือก>
    score: <0_to_10>
    anchors:
      - "D1: <หลักฐานจำนวนตัวอักษร>"
      - "D2: <หลักฐานความหมายแรกตามพจนานุกรม>"
      - "D3: <หลักฐานความหมายตามตัวอักษรของคำประสม>"
      - "D4: <หลักฐาน trial เทียบกับ real>"
      - "D5: <หลักฐาน run เทียบกับ test>"
      - "D6: <หลักฐานความมีชีวิต>"
      - "D7: <หลักฐานอุปกรณ์ขนาดใหญ่>"
    misses:
      - "<สิ่งที่ขาด — ลงเฉพาะที่ขาดจริง ไม่ต้องครบทั้ง 7 ข้อเสมอไป>"
```

**final** — ประกาศตัวที่เลือกและตัวสำรอง:
```yaml
final:
  pick: <ตัวเลือกที่ชนะ>
  backup: <อันดับสอง หรือ null>
```

### ขั้นที่ 3 · ตรวจสอบด้วย meta-rule

```bash
x rule check -r <naming-dir> naming.<user-task>.yml
```

OKR-creator (ที่ `template/naming.okr-creator.yml`) ทำการตรวจ 11 ข้อ (ผสมระดับ error และ warn):

| การตรวจ | ระดับ | ตรวจว่าอะไร |
|---|---|---|
| `okr-creator-001` has-goal-rule | error | ไฟล์มีกฎ `goal-*` อย่างน้อย 1 ข้อ |
| `okr-creator-002` has-keyresult-rules | error | ไฟล์มีกฎ `keyresult-*` อย่างน้อย 1 ข้อ |
| `okr-creator-003` has-task-specific-rules | error | ไฟล์มีกฎเฉพาะงานอย่างน้อย 1 ข้อ (ไม่ใช่ goal/keyresult) |
| `okr-creator-010` has-session-record | error | goal rule มีฟิลด์ `session:` |
| `okr-creator-011` prefer-answers-all-five | error | ตอบคำถาม init-004 ครบทั้ง 5 ข้อ |
| `okr-creator-012` init-verdicts-recorded | error | init_verdicts ไม่ว่าง |
| `okr-creator-013` scores-have-anchors | error | คะแนนทุกรายการมีรายการ anchors ที่ไม่ว่าง |
| `okr-creator-014` scores-no-below-6 | error | คะแนนทุกตัว >= 6.0 |
| `okr-creator-015` final-section-present | error | มีการประกาศ `final.pick` |
| `okr-creator-020` pick-backup-gap-le-1 | warn | คะแนน(pick) - คะแนน(backup) <= 1.0 |
| `okr-creator-021` top-pick-at-least-7 | warn | คะแนนของ pick >= 7.0 |

**ถ้าการตรวจระดับ error ใดไม่ผ่าน**: แก้ไฟล์แล้วรันใหม่ วิธีแก้ที่พบบ่อย:
- ฟิลด์ prefer ขาด → เพิ่มใน `session.prefer`
- คะแนนไม่มีหลักฐาน → เพิ่ม `anchors: [...]`
- คะแนน < 6 → ย้ายไป `init_verdicts` (ตัดทิ้ง) หรือปรับการตั้งค่าคะแนนใหม่
- final ขาด → เพิ่ม `final: { pick, backup }`

**ถ้าการตรวจระดับ warn ไม่ผ่าน**: ตัดสินใจว่าจะจัดการหรือบันทึกข้อแลกเปลี่ยนไว้

### ขั้นที่ 4 · ผู้ใช้เป็นคนเลือกชื่อสุดท้าย

สกิลเสนอ ผู้ใช้ตัดสินใจ ชื่อสุดท้ายถูกประกาศใน `session.final.pick` และ commit

## แบ่งระหว่างส่วนที่เป็นรูปธรรมกับส่วนที่เป็นความเห็นส่วนตัว

| รูปธรรม (อยู่ในไฟล์ / โค้ด) | ความเห็นส่วนตัว (ถามตอน init ไม่นับคะแนน) |
|---|---|
| ความหมายแรกตามพจนานุกรม | "ผมอยากได้แบบมีชีวิตหรือแบบนามธรรม" |
| จำนวนตัวอักษร | "ผมยอมรับโดเมน X ไหม" |
| กลุ่มความหมาย Trial / Real / Run / Test | "ผมยอมใช้อุปมาแบบทหารเรือหรือไม่" |
| ความหมายตามตัวอักษรของคำประสม | "ผมอยากได้รากศัพท์จีนหรืออังกฤษ" |
| การปนเปื้อนของ prior (unittest testcase, dryrun) | "ผมอยากได้คำสั้นมากกว่าคำที่อธิบายตัวเองชัด" |

## กฎ

- **ต้อง** สืบสวนเป้าหมายก่อน — กำลังตั้งชื่ออะไร มีบทบาทอะไร แนวคิดยึดหลักอะไร
- **ต้อง** เริ่มจาก `naming.template.yml` (ตัวแทน `TBD_*`) แล้วตัด / เติมตามความต้องการของงาน
- **ต้อง** ผลิต `naming.<user-task>.yml` (รูปแบบ `.rule`) ที่มีเป้าหมาย / ผลลัพธ์หลัก / กฎเฉพาะงาน / บันทึกเซสชัน
- **ต้อง** รัน `x rule check` พร้อม `template/naming.okr-creator.yml` เพื่อตรวจสอบบันทึกเซสชัน
- **ต้อง** ยึดคะแนนกับข้อเท็จจริงที่เป็นรูปธรรม — ห้ามปัดขึ้นหรือกดลงตามปฏิกิริยาของผู้ใช้
- **ต้อง** ให้ผู้ใช้เป็นคนเลือกชื่อสุดท้าย — สกิลเสนอ ผู้ใช้ตัดสินใจ
- **ห้าม** เพิ่มกฎที่เป็นความเห็นส่วนตัวลงใน `template/naming-concept.yml` — ให้ไปอยู่ใน `session.prefer` ของแต่ละงานแทน
